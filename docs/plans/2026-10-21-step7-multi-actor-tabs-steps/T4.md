## Proposed decisions

### 2026-10-22 · T4's MCP cursor and tool details (T4)
**Decided:** (B4–B7 of the step agent's brief and the builder's P1–P10) An explicit `tab` passes
through and never moves the cursor; only `browser_select_tab` and `browser_new_tab` move it. No `tab`
→ the cursor, or a first-touch `tabs.claim {active:true}` shared by concurrent calls; a stale claim
(generation counter) never lands. The cursor is lost on a 4002 `reconnected` and on a new client from
`BridgeLink` (`onClient`, failures swallowed), and the next untargeted result gets one line `Note: the
bridge daemon restarted, so this session's tab was lost; it now holds T<n> (the active tab).`, once
(re-armed if that call fails; dropped if the agent selects or opens a tab first). The cursor is not
cleared by `TAB_GONE`, `tabGone` or closing it. `browser_select_tab`/`browser_close_tab` have an
optional `tab` (T4.3 literal) and return an `isError` text without calling anything when it is
missing. Network tools: absent/`"active"` → the cursor, `"all"`/handles pass through, the numeric
form is gone from the MCP schema; an untargeted listing keeps the `Network — active tab:` label; an
`id` lookup claims nothing. `browser_status` prints `Active tab: [T<n>] …` from `current`, and `none`
with no fallback to `active`. A `newTab` answer without a handle (no-proto path) prints the id and
moves nothing.
**Why:** spec §6.5/§8.3 (the cursor does not follow the human); #57 (no destructive default on the
human's tab); no silent action on the human's tab after a tab is lost; NET-1/MUX-9 (T5.3 regression
text) and 0.7; #43.
**Instead of:** an explicit `tab` moving the cursor; required `tab` in the select/close schemas;
re-claiming the human's tab when the cursor's tab closes; the cursor's handle in the network header.
**Revisit if:** Step 8 adds `browser_use_active_tab` and the status cursor line (then the network
label and `Navigated active tab` wording), or a row shows an agent acting on an old handle after a
restart it was not told about.
**By:** Claude
