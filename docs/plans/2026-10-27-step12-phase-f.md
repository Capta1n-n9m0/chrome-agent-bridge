## Why

Phase F is the ergonomics phase of the roadmap: the things an agent driving the real profile keeps wishing for. Three
are carried from Steps 4 and 5 and the Step 11 plan: passing data into `browser_evaluate` without escaping it into the
string; reading what the page printed to its console (the Run 5 promise bug "would have been diagnosed much faster with
it", roadmap § Phase F); and a debugger session kept attached per tab, which both amortises the ~100 ms attach and the
banner flicker and is the base for event-driven work such as intercepting the native file chooser (Step 11 phase doc
0.13). Two candidates came from Step 11b: a `back`/`forward` that reaches history the bridge built alone (#308 (b),
named a Step 12 candidate by #311), and Run 17b's helper defects, which #320 put into Step 12's first live wave. Two
items are carried in the root Current state: a popup of a background opener gets no lease (#226), and the MCP trusted
tools' focus/input race (Step 10 Stage 0 F19).

### 0.4 B — `args` for evaluate (proposed — contract-level)

- **Shape.** `evaluate` and `evaluateSaveStart` gain an optional `args`, any JSON value. When `args` is present,
  `expression` is a **function source** called with `args` as its one argument, the shape Playwright's
  `evaluate(fn, arg)` uses (`"(a) => a.rows.length"`); without `args`, today's console-style expression is unchanged
  byte for byte. Mechanism to confirm at Stage 0: CDP `Runtime.callFunctionOn {functionDeclaration, arguments:
  [{value: args}], awaitPromise}` on the page's global object, the result through the existing serialiser
  (`extension/src/evaluate/result.ts`), `asRef` and `saveTo` unchanged.
- **Caps and refusals.** `args` must survive `JSON.stringify` (no `undefined`, function, `BigInt` or cycle), at most
  1 MiB serialised; else `BAD_PARAMS` with a fixed message naming the size or the type, never the value. The SDK
  checks first; the shared guard (`shared/src/protocol.ts`) and the extension check again.
- **SDK.** `tab.evaluate(fn, {args, timeoutMs})`, `evaluateToFile(fn, {args, …})`, `evaluateRef(fn, {args})`: option
  objects only, the eight values unchanged (`sdk/CLAUDE.md`). Strings only: no `String(fn)` of a real function,
  because tsx wraps inner named functions in `__name(…)` and the page throws (`recipes/CLAUDE.md`).
- **An old extension.** A loaded extension older than this stage ignores `args` and evaluates the function source as
  an expression, answering `kind: "function"`. The SDK, having sent `args`, turns that answer into `VERSION` with the
  reload hint, as `evaluateRef` does for a missing ref (`sdk/src/tab.ts`). Stage 0 attacks this.
- **MCP.** `browser_evaluate {args}` (a JSON value) and one description sentence; the schema baseline
  (`mcp/test/fixtures/tool-schemas-f45e3bf.json`) is re-pinned only by a recorded decision (decisions-archive/step10.md ·
  2026-10-25 · S2: the MCP schema baseline, a failed focus's answer, and the focus sentence (#214)).
- *Instead of:* (ii) a lexical `args` binding around the console-style expression (one form, but Stage 0 would have to
  show it creates no page global and keeps top-level `await` and the completion value; offered if (i) fails); (iii)
  the SDK pasting a JSON literal into the string (what agents do today; nothing gained, and an injection risk).

### 0.5 C — console messages and uncaught errors (user-gated — the mechanism, Q2; proposed — the shape)

- **(C1, recommended) Read on demand through CDP.** A new router method `consoleMessages {tabId, level?, limit?}`:
  inside one debugger session (D's when built), `Runtime.enable`, collect the messages Chrome reports for the page,
  `Runtime.disable`. *Not confirmed, so Stage 0 measures:* whether `Runtime.enable` reports messages logged **before**
  it (expected: V8 keeps a bounded per-page store and reports it on enable), the store's bound, whether uncaught errors
  come as `Runtime.exceptionThrown` the same way, whether a navigation clears it, and what an out-of-process frame's
  messages do. No page injection, no change to any page while no call runs. The banner shows during the call.
- (C2) Collect only while a kept session (D) is attached: a bounded per-tab log fed by `Runtime.consoleAPICalled` and
  `exceptionThrown`. Misses everything logged before the agent attached. The fallback if C1's replay does not exist.
- (C3) A main-world hook registered for every page at `document_start`: no banner and always on, but it runs inside
  every page of the profile (the human's too), the page can see, forge or silence it, and it needs a registered
  content script in the page's own world. Not recommended; offered because it is the only always-on option.
- **Entry shape (C1 or C2).** `{level, text, ts, kind: "console" | "exception"}`; `text` capped at 2 000 characters, at
  most 200 entries per reply, newest last; **no source URL and no stack** (URLs carry tokens, and a frame of a blocked
  host would show through). The SDK `tab.consoleMessages(opts)` (a `Tab` method; the eight values unchanged); the MCP
  `browser_console_messages {tab?, level?, limit?}` prints one line per entry through a formatter in `sdk/src/format`.
- **Class.** `consoleMessages` is class `tab` in `METHOD_CLASSES` (`extension/src/safety.ts`) and a tab method in
  `daemon/src/methods.ts` (lease-checked, no visibility lock): refused while disarmed, on a blocked, own or `file:`
  page, as `snapshot` is. Reading runs no page script, so the JavaScript switch does not gate it (contract-level,
  for the audit to attack: the conservative alternative is class `evaluate`, refusing it when JavaScript is off).
- *Not built here:* console lines appended to an `evaluate` result (a follow-up once C ships).
- *Note 2026-10-28 (session agent; decisions.md #334, #356):* the class above is superseded: `consoleMessages` is built as
  class `evaluate` (refused `JS_DISABLED` while JavaScript is off) until the user rules; the spec's S3a note agrees.

### 0.6 D — a kept debugger session per tab (user-gated — what the human sees, Q3; proposed — the lifecycle)

- **What.** A pure keeper (new module, injected attach/detach, unit-tested first) owns at most one session per tab:
  the first CDP call attaches, later calls reuse it, a reference count covers concurrent calls (Chrome allows one
  debugger per tab, `extension/CLAUDE.md`), and it detaches when the count is 0 for an idle bound (**5 s** proposed;
  the banner already lingers 3–14 s after a detach, SAFE-4 (b), R14-4b). `withDebugger` and every caller
  (`extension/src/debugger.ts`) go through it; no wire, daemon, SDK or MCP change.
- **Detach on:** a disarm (the keeper's sessions are in `debuggerSessions`, so `detachAll` covers them, #137); the
  tab's page becoming blocked, an own page or `file:` (seen in the existing top-level `tabs.onUpdated` listener, no new
  listener); the tab's close or replace; `chrome.debugger.onDetach` (`canceled_by_user`, `target_closed`,
  `replaced_with_devtools`: the human's Cancel and DevTools always win; the next call attaches again or gets today's
  `DEBUGGER_DEVTOOLS`); a worker restart (sessions do not survive it).
- **The gate still runs per call.** Reusing a session never skips the call's gate re-check before its first side
  effect (`runWithDebugger`'s check moves to before each use); a kept session never runs an `evaluate` while JavaScript
  is off, because the call is refused first.
- **Answers do not change** on any existing tool; the measured difference is time and the banner.
- *Instead of:* (b) a kept session only for event-driven features (E, later response bodies), every other call as
  today; (c) no D in Step 12.

### 0.7 E — the native file chooser (user-gated — Q4; proposed — the shape)

- **What.** `uploadFiles` gains `chooser: true`: the target (a ref or locator) is an element whose click opens the
  native file chooser, not a file input. In one call: `Page.setInterceptFileChooserDialog {enabled: true}`, a click
  that carries a user activation, wait for `Page.fileChooserOpened` (bound 5 s; `TIMEOUT` with a fixed message if
  none opens), `DOM.setFileInputFiles {files, backendNodeId}` from the event, interception off. The interception is
  **on only inside the call** and switched off on every path (success, refusal, error, timeout, disarm), so the
  human's own clicks open Chrome's dialog as today.
- **The same gate as `uploadFiles`:** class `upload`, the Upload folders rule at receipt (#236, #237), the file-URL
  toggle check (#245 (b)), the missing-file check before the attach (#299), `paths` caps, no path in a message or log
  (#242). No new method or code.
- **Which click, measured at Stage 0:** (i) `Runtime.evaluate {userGesture: true}` calling the element's `click()`
  (works on a background tab for history, Run 17b R17B-ACT-CTL; for the chooser unmeasured); (ii) a trusted CDP click,
  which needs `focusTab` first (`focusFirst`, #89, #106). (i) is preferred: no focus, no lock.
- **D or not.** Step 11's 0.13 assumed a kept session; events also arrive within one call's own session while it is
  attached. Stage 0 measures whether one call's session receives `Page.fileChooserOpened`; if it does, E does not
  depend on D (the order stays).
- **SDK and MCP.** `tab.upload(target, paths, {chooser: true})`; `browser_upload_file {chooser}` with one description
  sentence; the #214 baseline re-pinned by a recorded decision. Without `chooser`, today's path byte for byte.
- *Instead of:* intercepting for the life of a kept session (the human's dialogs would stop opening on that tab);
  treating a non-input target as a chooser without the flag (changes an existing refusal into an action).

### 0.8 F — `back`/`forward` onto bridge-built history (user-gated — Q5)

Chrome's back and forward skip pages no human acted on (#308; `extension/src/handlers/CLAUDE.md`), a protection against
pages that flood the history to trap the back button. Today a bridge `back` reaches only pages a human or an activating
call acted on (Run 17b R17B-BACK-NOACT, R17B-ACT-CTL).
- **(a) Don't build (recommended).** The limit stays documented; an agent navigates to the URL, or gives the page an
  activation first (an `evaluate`, as Run 17b did). Nothing sidesteps Chrome's protection.
- (b) Narrow: when Chrome refuses, go to the previous entry by CDP (`Page.getNavigationHistory`,
  `Page.navigateToHistoryEntry`) **only if** that entry is a page the bridge itself navigated to in this tab (the
  extension records its own committed navigations per tab). Pages a site added on its own are still skipped. The DNR
  tab rules are held as today (`handlers/history.ts`).
- (c) Broad: always go by CDP. Not recommended: it lands on entries a page added to trap the back button.

### 0.9 G — the carried items (user-gated — Q6)

- **G1, #226.** With the opener in the background, Chrome names another tab as a popup's opener, so the daemon's opener
  rule grants no lease (`daemon/CLAUDE.md`; R15-POP-2 (b)). (a) Keep it a documented limit. (b) Stage 0 measures
  whether `webNavigation.onCreatedNavigationTarget`'s `sourceTabId` names the real opener; if it does and needs no new
  permission, the extension's `tabCreated` carries it and the daemon's rule uses it (a lease rule change, #226's
  "Revisit if"); if it needs the `webNavigation` permission, that returns to the user (G12-2). **Recommended: (b),
  measure first.**
- **G2, F19.** Focus and input are two calls, so another actor's capture can come between them (`mcp/CLAUDE.md`; not
  seen live). (a) Keep it a known limit (**recommended**: never seen, and the fix changes the daemon's lock class).
  (b) One call: a trusted input with `focus: true` focuses and types inside the extension under the daemon's visibility
  lock (wire, daemon, SDK and MCP change). *Ruled 2026-10-27 (#321): (b) as a blocking action — the lock is held from the
  focus through the input and a settle pause after it; Stage 0 picks the mechanism (one call, or the daemon holding the
  lock across the focus and the input) and measures the pause.*

### 0.10 How every item passes the safety gate (proposed — contract-level, safety)

- **New methods enter both tables.** Only C adds one (`consoleMessages`): `METHOD_CLASSES` and `daemon/src/methods.ts`
  in the same commit; `safety-gate.test.ts`'s router scan and the daemon's table test pass unchanged in form. B and E
  add parameters to existing methods, which keep their classes (`evaluate`, `evaluateSaveStart`: `evaluate`;
  `uploadFiles`: `upload`). D and F add no method. Exempting or reclassifying a method is a forbidden fix.
- **The JavaScript switch.** `evaluate` with `args` is still class `evaluate`, so JavaScript off answers `JS_DISABLED`
  before anything runs (#202, #219). The activating click of E (0.7 (i)) runs a bridge-written script, not the
  agent's; it is gated as an upload, not as an evaluate (contract-level; the conservative reading — refuse E's click
  while JavaScript is off — is the audit's to weigh).
- **Nothing on the wire changes the safety state**; no item reads or writes it.
- **The log invariant** (root `CLAUDE.md`): product code never logs a URL, title, body, path, evaluated value or
  console text. B's `args`, C's entries and E's paths travel only in the reply to the caller (as evaluate values and
  snapshot text do today). The new modules have no log call; the log-scan allowlist (54 sites,
  `extension/test/log-allowlist.ts`) grows by **0**; `log-sentinel.test.ts` gains a sentinel string carried in `args`
  and in a fake extension's console reply, and asserts 0 occurrences in `daemon.log`. The existing `onDetach`
  diagnostic line (`extension/src/sw.ts`) logs a tab id and a reason only; D does not widen it.
- **What a refusal reveals** is unchanged: a refused `consoleMessages` answers as a refused `snapshot`.

## For the user at G12-0

Six questions. Each has a recommendation; the session agent puts them to you as plain-language write-ups and records
your answers in `docs/decisions.md` before Stage 0.

**Words used here.** *Banner*: Chrome's yellow "is debugging this browser" bar, shown while the bridge drives a tab
through Chrome's debugger. *Console*: the page's own log, what DevTools' Console tab shows. *File chooser*: the
"Open file" window a site opens when you click "Upload". *Held tab*: a tab one agent has claimed.

1. **Which items are in Step 12, in what order?** The Run 18 fix wave is already yours (#320). Candidates: B (pass data
   into evaluate), C (read the console), D (keep the debugger attached), E (answer the file chooser), F (back onto
   pages only the bridge visited), G1 (a popup of a background tab), G2 (the focus/input gap).
   **Recommended:** A, then B and C (small), then D, then E; F not built; G1 measured first; G2 not built.
2. **How should the bridge read a page's console?** (a) Ask Chrome on demand for what the page logged; nothing is put
   into any page; the banner shows during the read (**recommended**, if Stage 0 confirms Chrome keeps the earlier
   messages); (b) record only while the debugger is attached (misses earlier messages); (c) put a small recorder into
   every page you open (no banner, but it runs in your own pages too, and the page can see or fake it).
3. **May the banner stay up while an agent works?** Today it flickers on and off for each call and lingers 3–14 s
   after. (a) Keep one session per tab while the agent works and close it 5 s after its last call: faster, one steady
   banner (**recommended**); (b) keep it only for the features that need it (the file chooser); (c) not now.
4. **Should agents be able to answer a site's "Open file" window?** Today they can upload only into a visible file
   field. With (a) the agent clicks the site's Upload button and Chrome's window is answered for it, only during that
   one call and only with files from your Upload folders; your own clicks still open the normal window
   (**recommended**); (b) not built.
5. **Should `back` reach pages only the bridge visited?** Chrome skips pages nobody clicked on, to stop sites from
   trapping the back button. (a) Keep Chrome's rule; agents go to the address instead (**recommended**); (b) only when
   Chrome refuses, step back to a page the bridge itself opened in that tab; (c) always step back through the
   debugger (it can land on pages a site added to trap you).
6. **The two carried items.** G1: a popup opened by a background tab is not handed to the agent that holds the opener.
   (a) Keep it a known limit; (b) Stage 0 checks whether Chrome can tell the real opener; build it if no new permission
   is needed, else ask you again (**recommended**). G2: another agent's screenshot could slip between a trusted click's
   focus and its input. (a) Keep it a known limit, never seen (**recommended**); (b) merge focus and input into one call.
