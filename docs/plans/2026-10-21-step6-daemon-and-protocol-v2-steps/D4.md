## 4. Deviations from the phase doc

Recorded in the phase doc as an "As built 2026-10-22 (D4)" note under Stage D4:
1. The 10 s budget runs per spawn cycle and restarts at the client's own handover (a handing-over
   `connect()` may take ~20 s). Not a lowering of the limit; a test pins it.
2. One spawn per cycle, not one per refused knock.
3. After its own handover, "knock until REFUSED" is refined: an old-build daemon still answering before our
   spawn counts as draining; a matching build is accepted at once.
4. Reconnect after 4002 never hands over; old build still answering at the deadline after our handover → `VERSION`.
5. Each `tryConnect` has a handshake timeout = remaining budget (floor 100 ms; worst case 10.1 s).
6. Pre-socket configuration failures, the give-up and close 4001 use `NOT_CONNECTED`.
7. `BRIDGE_TOKEN` is trimmed (`mcp/src/config.ts` reads it raw — D5 replaces that read with `resolveToken`).
8. `BridgeClient` extras beyond the checkbox: `welcome`, `extensionConnected`, `on("reconnected")`.

## 5. Proposed decisions

### 2026-10-22 · The SDK reports configuration and connection failures as NOT_CONNECTED
**Decided:** A missing token, a missing daemon build, a bad `BRIDGE_PORT`, the 10 s give-up and close 4001
reject with `NOT_CONNECTED`; `VERSION` is kept for build/protocol mismatches and the missing welcome.
**Why:** Spec §10's 22 codes have no configuration or authentication code; `NOT_CONNECTED` is what the MCP's
5 s retry path already treats as "not reachable yet"; each message names its cause (never the token).
**Instead of:** `BAD_PARAMS` (meant for a method's params); `VERSION` for 4001; a new code (spec change).
**Revisit if:** Step 8 adds an authentication or configuration code to spec §10. **By:** Claude (proposed; contract-level — for user review)

### 2026-10-22 · A reconnect after 4002 never hands the daemon over
**Decided:** `BridgeClient`'s 4002 reconnect runs the knock with the handover disabled; a build mismatch
there rejects with `VERSION` naming both builds (spawning on a refused port is still allowed). After a
client's own handover, an old build still answering at the deadline also rejects with `VERSION`.
**Why:** Decision #10 caps handovers per `connect()`, but every 4002 reconnect is a fresh knock, so two
clients on different builds could hand the daemon back and forth (verifier simulated 2 handovers, and the
loser got a misleading `NOT_CONNECTED`). Disabling the handover on reconnect is the conservative reading
(fails rather than loops); `handover-race.test.ts` pins ≤ 1 shutdown and a `VERSION` loser at 7 lags.
**Instead of:** Letting each reconnect hand over once (the letter of #10, not its purpose); a give-up as
`NOT_CONNECTED`. **Revisit if:** D6 shows a legitimate upgrade path that needs a reconnecting client to
hand over (e.g. a long-running MCP after `npm run build` with the old daemon still alive). **By:** Claude (proposed; contract-level — for user review)

### 2026-10-22 · The knock's 10 s budget runs per spawn cycle, with a handshake timeout per attempt
**Decided:** The 10 s limit restarts at the client's own handover; the knock spawns once per cycle; each
`tryConnect` gets the remaining budget (floor 100 ms) as a WebSocket handshake timeout (`ETIMEDOUT`, no spawn).
**Why:** The handover starts a new spawn cycle (0.7's diagram); repeated spawns only lose the bind race; a
port holder that accepts TCP and never upgrades kept `connect()` pending past 14 s before the timeout.
**Instead of:** One 10 s budget for the whole `connect()`; a spawn per refusal; no handshake timeout.
**Revisit if:** D6 sees a handover take longer than 10 s, or a spawned daemon dying silently. **By:** Claude (proposed)

### 2026-10-22 · BridgeClient exposes welcome, extensionConnected and on("reconnected") in Step 6
**Decided:** Beyond the D4 checkbox, `BridgeClient` has read-only `welcome` / `extensionConnected` getters and
an `on("reconnected", cb)` listener; `index.ts` still exports exactly the five D4.3 values.
**Why:** `connect()`'s extension wait needs both getters; `on("reconnected")` is the hook decision #11 asks
Step 6 to leave for the Step 7/8 cursor clear. Undoable; Step 8 owns the final surface.
**Instead of:** Package-internal accessors only (would force D5/Step 7 to reach into internals).
**Revisit if:** Step 8's SDK surface review. **By:** Claude (proposed; public surface — for user review)

## 6. Findings

- Pre-registered checks: none failed.
- Open NITs from the re-check (not fixed; none blocks D3/D5):
  1. Removing `ws.terminate()` on a handshake timeout fails no test (mutation F2c); the ETIMEDOUT test should
     assert the server-side socket closes. Follow-up for D5 or Step 8.
  2. A non-4002 close landing between the client attaching and the extension wait starting is missed:
     `connect()` waits the full `waitForExtensionMs` and reports "is Chrome open". Very narrow window
     (reproduced with a probe). Fix: if the client has already failed when the wait starts, throw that failure.
  3. Close-reason masking catches only the whole token; the non-4002 close message includes the daemon's
     reason unmasked. The daemon never puts the token in a reason today (D2).
- Measured fact worth a `CLAUDE.md` gotcha (session agent's call): with `ws`, several frames in one TCP read
  are emitted synchronously before any promise continuation runs, so a listener that settles a promise and
  is removed later (in a `finally`) still swallows the frames behind the one it waited for. Unsubscribe
  inside the callback, and let the transport buffer frames while no listener is attached.
- `mcp/src/config.ts` reads `BRIDGE_TOKEN` raw while the SDK trims it — D5 should use `resolveToken`.
