### Contracts as built (Step 7 and D4 depend on these)

**Hello.** The first frame on every socket. The token is checked first, then the role.
- An absent `role` or `role: "extension"` makes the socket *the* extension. A newer one replaces the
  older one; it is never put in the registry.
- `role: "client"` joins the registry with ids `c1`, `c2`, …, never reused within a process.
- A client hello with no `name` is listed as `"unnamed"`.

**Welcome**, sent on every accepted hello:
```
client:    {type:"welcome", build, proto:2, clientId:"c<n>",       extensionConnected:<bool>}
extension: {type:"welcome", build, proto:2, clientId:"extension", extensionConnected:true}
```
- `build` is the `WsHost` option `build`, default `"dev"` (`DEFAULT_BUILD`). D3 wires the real
  sha256.
- The extension's welcome is sent after the bridge takes the new connection.
- The v1 extension ignores the welcome: `extension/src/router.ts:18` returns null for a frame
  without `id` and `method`.

**`daemon.status`** returns:
```
{build, uptime, extensionConnected, clients:[{id, name, since}], port}
```
`uptime` is in milliseconds since `listen()`. `since` is the epoch time in milliseconds when the
client joined. A client that leaves drops out of the list.

**`daemon.shutdown`** sends the result `{ok:true}` to the caller first. Then `host.shutdown(4002)`
runs, which:
- stops accepting new connections;
- sends `close(4002, "upgrading")` to every socket, the clients and the extension alike;
- waits up to 1 s, then terminates whatever is still open.

It is idempotent and does not exit the process; D3 wires the exit. A hello that arrives during
shutdown gets no welcome.

**Requests** from clients have the form `{id, method, params?, timeoutMs?}`. Validation:
- The reply always carries the client's `id` verbatim. The daemon remaps the id to its own
  `ExtensionConnection` id (`"1"`, `"2"`, …), so ids that collide across clients are safe.
- Any other `daemon.*` method gets `UNKNOWN_METHOD` ("unknown daemon method: <m>") and is never
  forwarded.
- `BAD_PARAMS`, with the id echoed, for:
  - an id that is a number or an empty string;
  - a method that is missing, empty or not a string;
  - `params` present but not a plain object (`null` included);
  - `timeoutMs` present but not a finite number.
- A frame that is not a JSON object, or that has no string or number id, is dropped and counted in
  `stats().ignoredClientFrames`.
- The frame forwarded to the extension stays `{id, method, params}`; `timeoutMs` is not forwarded.

**Timeouts.** The daemon waits `daemonWaitMs(t) = clamp(t ?? 30000, 100, 600000) + 5000`. The
constants are exported: `MIN_TIMEOUT_MS`, `MAX_TIMEOUT_MS`, `DEFAULT_TIMEOUT_MS`, `DAEMON_SLACK_MS`.

**Error envelope:** `{id, error:{code, message, data?}}`. `code` is always present.
- No extension connected: `NOT_CONNECTED`, with today's text ("Extension not connected — is Chrome
  open…") or the stored unavailable reason.
- The extension leaves while calls are in flight: `NOT_CONNECTED` "extension disconnected".
- The daemon's own wait runs out: `TIMEOUT` "Timed out after Nms calling <method>".
- An error from the extension is passed through `fromWire`, so a v1 `{message}` becomes `INTERNAL`.
- Any other thrown error becomes `INTERNAL` with its message.
- A result of `undefined` is sent as `null`.

**Close codes:**
- **4001** for a failed handshake. The reason is one of `"expected hello handshake"`,
  `"invalid token"` or `"unknown role"`; none echoes a field value.
- **4002** with the reason `"upgrading"` from `daemon.shutdown`.
- Any other `shutdown(code)` uses the reason `"daemon shutting down"`. D3 uses 1001.
- `WsHost.close()` (used by the MCP and the tests) still terminates every socket, and clients see 1006.

**Events:**
- **`extensionStatus`.** `{event:"extensionStatus", params:{connected}}` goes to every registered
  client:
  - `true` on each extension hello;
  - `false` only when the socket that closes holds the bridge's *current* connection (B7). An old
    extension socket closing after a newer one connected sends nothing.
- **Events from the extension.** `{event, params}` frames are counted in `stats().extensionEvents`.
  Nothing is sent to any client.

**Heartbeat.** The heartbeat runs on every socket, clients included (F34). A client that misses a
pong is terminated and removed from the registry. The log line names only the role.

## 4. Deviations from the phase doc

1. **`validateHello` keeps its v1 return shape `{ok:true}`.** The new `parseHello` returns
   `{ok, role, name, build}`, and `wsHost` uses it.
   - Why: the existing test `handshake.test.ts` "accepts a valid hello" pins `toEqual({ ok: true })`,
     and existing tests stay unedited. Under the conservative rule of the SPEC-DISCREPANCY PROTOCOL,
     every existing test has to behave identically. The verifier confirms the two cannot both hold
     without a trick, such as a prototype getter.
   - The phase doc now carries a dated *Superseded* note on that checkbox.
2. **`timeoutMs` is not copied onto the frame forwarded to the extension.** This follows decision
   0.2: routing is dumb and the v1 extension ignores the field. Spec §10 says "same, id remapped",
   which is looser.
3. **`daemon/package.json` still does not declare `@bridge/shared`.** Adding it needs a root
   `package-lock.json` edit, which is outside the D2 lane. The package resolves through the
   workspace link today. Left for D3 (verifier NIT 7).
4. **The `daemon` package's `exports` do not list `./registry` or `./route`.** Nothing outside
   `daemon/` imports them yet.

## 5. Proposed decisions

### 2026-10-22 · validateHello keeps its v1 shape; parseHello carries the role
**Decided:** `parseHello(data, token)` returns `{ok:true, role, name?, build?}` or
`{ok:false, reason}`. `validateHello` is a wrapper that keeps returning `{ok:true}` or the reason.
**Why:** The D2 checkbox would change the return shape that the existing test pins with
`toEqual({ok:true})`, and existing tests stay unedited (`D2-verifier.md` finding 1).
**Instead of:** Editing the existing test's expected object; hiding `role` behind a non-enumerable
property.
**Revisit if:** D5 deletes the last caller of `validateHello`. Then it can go.
**By:** Claude (proposed)

### 2026-10-22 · A client's numeric or empty request id gets a BAD_PARAMS reply
**Decided:** The id is echoed verbatim with `BAD_PARAMS`. Only a frame whose id is absent, or of
another type, is dropped and counted.
**Why:** B8 rules it. Otherwise a client that sends `id: 1` hangs until its own timer runs out.
**Instead of:** Silently dropping every id that is not a string.
**Revisit if:** The SDK ever sends numeric ids.
**By:** Claude (proposed)

### 2026-10-22 · The daemon does not forward timeoutMs to the extension in Step 6
**Decided:** The frame sent from the daemon to the extension stays `{id, method, params}`. The
clamped wait applies only on the daemon's side.
**Why:** Decision 0.2 (routing is dumb). The v1 extension ignores the field.
**Instead of:** Copying the clamped `timeoutMs` onto the forwarded request.
**Revisit if:** Step 7's extension wants the envelope timeout.
**By:** Claude (proposed)

### 2026-10-22 · Defaults before D3: build "dev", client name "unnamed", ids c1, c2, …
**Decided:** `WsHost` takes `build` as an option, defaulting to `"dev"`. A client hello without a
name is listed as `"unnamed"`. Client ids are `c<n>` and are never reused within a process.
**Why:** D3 owns the real build hash, and `daemon.status` needs a name for every client.
**Instead of:** An empty build or name; using the client id as the name.
**Revisit if:** A real daemon could ever report `"dev"`. D3 must always pass the hash.
**By:** Claude (proposed)

### 2026-10-22 · A hello with an unknown role closes 4001 with the reason "unknown role"
**Decided:** The role is checked after the token, and an unknown role gets its own close reason. No
field value is echoed.
**Why:** It is a clearer diagnostic, and it leaks nothing.
**Instead of:** The generic "expected hello handshake".
**Revisit if:** —
**By:** Claude (proposed)
