```
Daemon: connected on 127.0.0.1:<port> (build <build>, up <round(uptime/1000)>s)
```

## 5. Proposed decisions

### 2026-10-22 · The MCP notices a closed daemon connection by checking `client.connect()`
**Decided:** `mcp/src/link.ts` checks the client it holds with `client.connect()`. It does this
every 5 s and after any call that rejects with NOT_CONNECTED. On an open client that call resolves
at once with no wire traffic; on a client whose connection closed with a code other than 4002 it
rejects at once with that failure. On a rejection the MCP stores the message, closes and drops the
client, and calls a fresh `connect()` on the 5 s chain. Attempts never overlap.
**Why:** Decision #15 asks for exactly this. The SDK's public surface has no failure event:
`onClientFailure` is package-internal, and D5's lane excludes `sdk/`. The verifier measured the
fresh `connect()` 4993 ms after a 1001 close, and saw a 4002 reconnect leave the client in place.
**Instead of:** Exporting `onClientFailure` from the SDK, which is outside the lane and grows the
public surface; checking with `status()`, which sends a message every 5 s.
**Revisit if:** Step 8's SDK surface adds a public close or failure event, or reconnect.
**By:** Claude (proposed)

### 2026-10-22 · `mcp/src/config.ts` keeps only the actor name, and the daemon's interim exports go
**Decided:**
- `config.ts` holds `actorName(pid = process.pid)`. `connect()` resolves the token and the port
  (0.10), and the retry constant lives in `link.ts`.
- `daemon/package.json` loses its whole interim `exports` block, since nothing outside `daemon/`
  imports it.
- `mcp/package.json` declares `ws`, because the bundle imports it at runtime.
- `validateHello` stays (decision #20: a test pins it).

**Why:** These are the as-built register's carried items and decision #19's "Revisit if" (D5
removes the interim wiring).
**Instead of:** Deleting `config.ts`; keeping `./bridge`/`./connection`/`./wsHost` exported.
**Revisit if:** A later stage needs a daemon import from another package.
**By:** Claude (proposed)

### 2026-10-22 · With Chrome closed, the MCP holds no daemon client (accepted for Step 6, documented)
**Decided:** Keep `connect({ name })` with the default 15 s wait for the extension. With Chrome
closed:
- `browser_status` shows `Daemon: not connected` and `Problem: Extension not connected — … (waited
  15000 ms on port 9234)`, although the daemon is up;
- the MCP opens and closes a daemon client about every 20 s;
- for the first ~15 s, tools say `connecting to the bridge daemon…`.

This is documented in `setup.md` Troubleshooting and in e2e row CONN-2 (b).
**Why:** The stage text says `connect({ name })`. The SDK has no "connected without the extension"
mode: `connect()` closes its client when the wait expires, so a shorter wait does not help. Adding
such a mode is an SDK surface change, which is outside D5 (the verifier's F2; the builder's finding 2).
**Instead of:** An SDK option to return a client whose welcome says the extension is down, so that
`browser_status` could say "daemon connected, extension not connected" and the daemon's client list
would not churn.
**Revisit if:** D6 finds the churn or the message confusing, or Step 8 reviews the SDK surface.
**By:** Claude (proposed; touches the SDK surface, so for user review)
