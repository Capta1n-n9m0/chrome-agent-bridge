## 5. Proposed decisions

### 2026-10-25 · S4: a primitive completion value crosses the CDP leg whole; `saveTo` records it and S7 measures it
**Decided:** keep `evaluate`'s semantics for `saveTo`; objects and promise-valued completions (any `return …`,
`fetch(…).then(…)`) are sliced on the CDP leg; a primitive completion value arrives whole in `Runtime.evaluate`'s
reply (CDP gives primitives no `objectId`) and is sliced from the worker on, so no runtime message or WS frame grows
with it; the description and SDK docs advise `return …` for a very large value; S7 measures SAVE-PRIM and SAVE-IDONLY.
**Why:** no semantics-preserving fix exists (builder §7, verifier §4: `objectGroup`/`$_` still returns the reply whole,
an object-wrapping rewrite loses `replMode`'s top-level `await` and re-declaration and may hit CSP; `idOnly` is
documented as the default behaviour, unverified); (a) is the conservative choice — no new refusal, every tool unchanged.
**Instead of:** (b) a save-only rewrite of the expression; (c) `serializationOptions: idOnly` (unproven); (d) a new
size refusal for primitive completions. **Revisit if:** SAVE-PRIM fails at ≥ 64 MiB (then (d) with the measured bound),
or SAVE-IDONLY shows an `objectId` for a primitive (then (c)). **By:** Claude (proposed — touches 0.4 (user) and F2's
amendment under #205; **for user review**)

### 2026-10-25 · S4: the `saveTo` wire methods and their params
**Decided:** three tab methods `evaluateSaveStart {tab, expression, timeoutMs?}` → `{id, bytes, kind:"string"|"json"}`,
`evaluateSaveChunk {tab, id, offset, length?}` → `{data}` (base64, ≤ 1 MiB), `evaluateSaveEnd {tab, id}` →
`{released}`; class `"evaluate"` in `METHOD_CLASSES`; `TAB_METHODS` in `daemon/src/methods.ts`, no lock. **Why:**
#205/F4, mirroring `downloadStart`/`Chunk`/`End`. **Instead of:** a `store` flag on `evaluate`; tab-less pulls; a
sha256 in the start result. **Revisit if:** S7 needs the hash extension-side. **By:** Claude (contract-level, **for
user review**)

### 2026-10-25 · S4: a pull of an unknown, expired, lost or other-tab id is `INTERNAL`, as `downloadChunk`'s
**Decided:** plain `Error` → `INTERNAL` `Unknown or expired evaluateSave id: <id>`, the same text for another tab's id
(reveals nothing); an end naming another tab → `{released:false}`; the SDK removes `.part` and sends the end. **Why:**
the download analogy; V8. **Instead of:** `BAD_PARAMS` or `TAB_UNKNOWN`. **Revisit if:** clients need to tell "lost"
from a bug. **By:** Claude (contract-level — a code chosen for a refusal; **for user review**)

### 2026-10-25 · S4: store caps — 5 min TTL, 8 entries, 256 MiB; oldest evicted; over-cap is `BAD_PARAMS`
**Decided:** as built; a value over 256 MiB is refused `BAD_PARAMS` before any slice is read (code units checked in the
page, bytes again before storing); eviction is by age across all tabs, so one client's saves can push out another's
in-progress save, which then fails cleanly (verifier MINOR 1, measured). **Why:** worker memory (~3× the value
transiently); download's eviction model. **Instead of:** no cap; per-tab quotas; refusing a start when full ("busy",
a new refusal). **Revisit if:** S7's SAVE-64 shows memory pressure, a user needs more than 256 MiB, or concurrent
actors' saves collide in practice. **By:** Claude (contract-level — a refusal code and cross-actor behaviour; **for
user review**)

### 2026-10-25 · S4: the value refusals
**Decided:** `undefined`, a function, a symbol, a Map, a Set, a DOM node (`instanceof Node` or a `[object Node]`
prototype in the chain — a plain object with `nodeType`/`nodeName` keys saves), or a value whose `JSON.stringify` is
`undefined` → `BAD_PARAMS` with fixed texts; `JSON.stringify` throws → `PAGE_ERROR {name:"TypeError"}` with a fixed
text (never its own message, which can quote keys); the page's own exception → `PAGE_ERROR` as `evaluate` renders it.
**Why:** F12/#207; verifier finding 2. **Instead of:** duck typing; echoing `JSON.stringify`'s message. **Revisit if:**
a page that tampers with prototypes matters (then a node may save as `{}`). **By:** Claude (contract-level per #207;
**for user review**)

### 2026-10-25 · S4: the SDK form and its exported types
**Decided:** `Tab.evaluateToFile(expression, {path, overwrite?, timeoutMs?})` → `{path, bytes, kind, sha256}` plus the
`BridgeClient` mirror; new exported **types** `EvaluateToFileOptions`, `EvaluateToFileResult`; values stay eight;
`saveEvaluateToFile` and `checkSaveTarget` also reachable through the existing `@bridge/sdk/download` subpath (the MCP's
door; no `package.json` change). **Why:** 0.4, F21, the eight-value rule. **Instead of:** a ninth value; a new `./save`
subpath. **Revisit if:** the user wants the subpath additions withdrawn or public. **By:** Claude (contract-level —
the SDK's exported surface; **for user review**)

### 2026-10-25 · S4: the file finish — hard link without `overwrite`, rename with it; a stuck `.part` fails the save
**Decided:** with `overwrite: true` the finish is `rename`; otherwise `link(part, target)` (`EEXIST` → `BAD_PARAMS`
"exists") then remove `.part`, falling back to a re-check and `rename` when the file system cannot hard-link (`EPERM`,
`ENOTSUP`, `EOPNOTSUPP`, `EXDEV`, `ENOSYS`); a failed `.part` removal is retried once, and a second failure rejects
`INTERNAL` (naming the two paths, no value text) and keeps the complete target. **Why:** `rename` replaced a file that
appeared after the check (verifier finding 5); success must never be reported while a second name holds the value
(#207; R1-1). **Instead of:** re-check + rename only; swallowing the removal failure; deleting the target too.
**Revisit if:** a live Windows run shows transient unlink failures longer than one retry. **By:** Claude

### 2026-10-25 · S4: two time bounds for a save; JavaScript-off drop reads the memory copy
**Decided:** `timeoutMs` bounds the page's work; the read-out gets 120 s more; the client waits `timeoutMs + 125 s`. The
JavaScript-off store drop reads `SafetyStore.memory` (fails closed). **Why:** a 64 MiB value is 64+ slice calls;
Step 9's import invariants on `SAFETY_KEYS`. **Revisit if:** SAVE-64's read-out nears 120 s. **By:** Claude

## 6. Findings

- **F2 primitive path** — §1 (escalated for the user; MINOR in the verifier's grading).
- **Gotcha candidates for `CLAUDE.md` (S8), as measured facts:**
  1. CDP returns a primitive (string, number, boolean, null) inline in `Runtime.evaluate`'s reply — there is no
     `objectId` to slice — so only an object or a promise completion can be read out in slices; `saveTo` keeps a
     large string off one reply only when it is produced with `return …` (by protocol + fake-CDP tests; the live
     reply size is SAVE-PRIM's to measure).
  2. The `saveTo` store lives in the service worker's memory: a worker restart, a disarm, JavaScript off, the tab's
     close or replace, or 5 min idle drops it; a later pull answers `INTERNAL Unknown or expired evaluateSave id`
     and the SDK removes `.part` (unit + cross-package tests).
  3. `fs.rename` replaces an existing target on Windows and POSIX alike, so a no-overwrite finish needs `link` (fails
     `EEXIST`) — measured on NTFS by the verifier.
- Pre-existing, not S4: `npx tsc --noEmit -p recipes/tsconfig.s6.json` fails at `f4c0ff2` too (Step 9's
  `s9-rules.test.ts` imports `extension/src/tabs.ts` without chrome types) — for the session agent / S8.
