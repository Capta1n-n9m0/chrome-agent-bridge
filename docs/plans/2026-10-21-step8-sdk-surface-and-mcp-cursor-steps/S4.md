## 4. Deviations from the phase doc

- No subclass: the fields are optional properties on the shared `BridgeError` (#83 item 3, #86 item 6).
- `report()` is capped at 60 lines in total, not only its snapshot part (stricter; both hold).
- The window is anchored on a candidate/match whose ref survived the remap, else the top. It is never
  anchored on the failing call's own ref (that number is re-minted by the report's snapshot), so
  `REF_STALE` reports start at the top. F25's "around the ref for REF_STALE" is not built, for that
  reason.
- `error.data.candidates[i].ref` / `matches[i].ref` are rewritten or deleted when a report is attached
  (§5, first entry). With `failureReports: false` the data is untouched.
- Raw `client.call()` is not enriched (0.5 says "every SDK call"; F25 asked). The MCP, which uses raw
  calls, behaves identically.
- `network({id})` and `download` are wrapped too (any attach-set code from a call the Tab makes).

## 5. Proposed decisions

### 2026-10-23 · A failure report's snapshot renumbers refs; the SDK rewrites or drops the refs in the error — for user review
**Decided:** a failure report takes one `snapshot`, which resets the tab's RefMap exactly like a
script's own `snapshot()` (refs from before the failure are void; documented in the `error.ts` header,
the `snapshot` field's JSDoc, the `failureReports` JSDoc and a line in `report()`). When the snapshot
attachment succeeds, each `error.data.candidates` / `matches` item with a non-empty role gets the ref of
the one snapshot element with the same role and name; an item with zero or several such elements, or
with no role (every `LOCATOR_AMBIGUOUS` match carries none; a `{text}`/`{css}` candidate with role
`""` is not a snapshot element) has its `ref` deleted. When the snapshot was attempted but rejected or
cut, every such ref is deleted and the report says refs were withheld. `report()` prints only refs of
the attached snapshot and anchors only on them.
**Why:** verifier F1/R1-1, measured: without it a script acting on `err.data.candidates[0].ref`, or
reading the report, acts on another element. 0.5 prescribes the snapshot attachment; the reset is the
snapshot's own rule, so the SDK makes the error consistent with it. Deleting is the safe direction: a
missing ref makes a script re-locate; a wrong ref acts on the wrong element.
**Instead of:** (a) leaving the data as sent (a silent misdirect); (b) a snapshot that does not reset
the RefMap — an extension/wire change outside S4's lane, the better long-term fix, for the user;
(c) no snapshot for `LOCATOR_*` codes (contradicts 0.5); (d) name-only remapping (R1-1: wrong element).
**Revisit if:** the user wants (b); S5/S6 show role-locator matches needing their refs (they now always
lose them — verifier re-check 2 side effect).
**By:** Claude (proposed; contract-level — changes the values in a wire error's `data` and the ref
lifetime a script sees — for user review)

### 2026-10-23 · S4's failure-report details

### 2026-10-23 · A failing screenshot, focusTab or download is enriched literally (F25) — for user review

## 6. Findings

- No pre-registered check failed.
- Measured (jsdom, real content-script code): any `snapshot` call renumbers the refs a `locate` minted
  just before it; refs are walk-order numbers reset per snapshot, so a held ref silently names another
  element once the page changed, rather than answering `REF_STALE`. Worth a `CLAUDE.md` gotcha at S7
  (stated as measured by the S4 verifier in jsdom, not live).
- The covered-window case (kickoff §4 (c)): on a window fully covered by other windows the attach
  screenshot lands in `attachErrors` within 5 s (the cut), but the extension's switch continues: the
  human may see the failed tab in front for up to ~30 s (R9-RESTORE: `TIMEOUT` at 35 119 ms, previous
  tab back at +30 026 ms). A minimized window → `WINDOW_MINIMIZED` in `attachErrors`; another actor's
  lock → `LOCK_TIMEOUT` or the cut. Stated in the `error.ts` header comment. Not measured live in S4.
- A cut attach call stays pending until its own client timer (≈ 11 s: 5 s + daemon 5 s + client 1 s);
  the socket keeps the process alive until `client.close()` anyway; no listener leak (verifier F7).
